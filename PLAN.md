# Leash AI - Implementation Plan

This document outlines a high-level plan for implementing the Leash AI project in Rust. The plan is broken into phases and parallel workstreams, designed to allow multiple agents to tackle different components simultaneously.

All implementation details MUST adhere to the specifications laid out in `CORE_SPEC.md` and the conceptual guides in the `docs/` directory.

## Guiding Principle: Parallel Development

The project will be structured as a [Cargo workspace](https://doc.rust-lang.org/book/ch14-03-cargo-workspaces.html) with multiple crates. This allows for clear separation of concerns and enables agents to work on independent crates with minimal friction. Each workstream corresponds to one or more crates within the workspace.

## Phase 1: Foundation (Contracts & Types)

This phase is foundational and must be completed first, but the two workstreams can be done in parallel. The goal is to establish the core, shared data structures and API contracts that all other components will depend on.

### Workstream 1: Core Types Crate (`leash-ai-core`)
*   **Agent Focus:** Data Structures Specialist
*   **Task:** Create a new crate, `leash-ai-core`, that defines all shared data structures and domain types.
*   **Outputs:**
    *   Rust structs for `Policy`, `ApprovalRequest`, etc. based on `CORE_SPEC.md`.
    *   The primary `CapabilityGrant` (JWT claims) struct.
    *   The `AuditEvent` struct.
    *   Shared error types and enums (e.g., `ResourceType`, `RequestState`).
*   **Dependencies:** None (This is the root dependency for other crates).

### Workstream 2: API Contract Crate (`leash-ai-api`)
*   **Agent Focus:** API Design Specialist
*   **Task:** Create a new crate, `leash-ai-api`, to define the complete gRPC API contract.
*   **Outputs:**
    *   `.proto` files defining all services (`RequestService`, `ApprovalService`, `AuditService`), messages, and enums as specified in `CORE_SPEC.md`, Section 8.
    *   Build script (`build.rs`) using `tonic-build` to generate Rust code from the `.proto` files.
*   **Dependencies:** `leash-ai-core` (for reusing types in messages if desired).

---

## Phase 2: Core Implementation (Parallel Sprints)

Once Phase 1 is complete, these workstreams can be developed largely in parallel. Each agent will work within their designated crate(s), relying on the contracts defined in Phase 1.

### Workstream 3: Daemon Crate (`leashd`)
*   **Agent Focus:** Main Application & Logic Specialist
*   **Task:** Build the main daemon application that implements the gRPC services.
*   **Outputs:**
    *   A binary crate `leashd`.
    *   Implementation of the gRPC service traits generated by `tonic`.
    *   The core state machine logic from `CORE_SPEC.md`, Section 1.
    *   The policy evaluation engine from `CORE_SPEC.md`, Section 2.
    *   Initial integration points for the database and backend layers (using traits and mock implementations).
*   **Dependencies:** `leash-ai-core`, `leash-ai-api`, `leash-ai-db`, `leash-ai-backend` (trait).

### Workstream 4: Database Crate (`leash-ai-db`)
*   **Agent Focus:** Database & Persistence Specialist
*   **Task:** Implement the data persistence layer as defined in `CORE_SPEC.md`, Section 5.
*   **Outputs:**
    *   A library crate `leash-ai-db`.
    *   A `DatabaseConnection` struct that handles all SQLite interaction.
    *   Functions to store, retrieve, and query `Request` and `AuditEvent` records.
    *   Implementation of the append-only, hash-chaining logic for audit log immutability.
*   **Dependencies:** `leash-ai-core` (for the data models), `sqlx`.

### Workstream 5: Backend Crates (`leash-ai-backend-*`)
*   **Agent Focus:** Backend & Integration Specialist(s)
*   **Task:** Implement the "Backend Contract" (Section 7) and create concrete backend implementations. This is the most parallelizable task. A different agent can be assigned to each backend.
*   **Outputs:**
    *   A shared `leash-ai-backend` crate defining the `SecretBackend`, `PackageBackend`, and `CliBackend` traits.
    *   A separate crate for each implementation (e.g., `leash-ai-backend-keychain`, `leash-ai-backend-homebrew`).
*   **Dependencies:** `leash-ai-core`.

### Workstream 6: Client SDK Crate (`leash-ai-client`)
*   **Agent Focus:** Client Library Specialist
*   **Task:** Build a user-friendly, async Rust client for interacting with the `leashd` gRPC API.
*   **Outputs:**
    *   A library crate `leash-ai-client`.
    *   A simple `Client` struct with methods like `request_secret(...)`, `execute_command(...)`, etc.
    *   Handles connection management and authentication with the daemon.
*   **Dependencies:** `leash-ai-api`, `leash-ai-core`.

### Workstream 7: Management CLI Crate (`leash`)
*   **Agent Focus:** CLI Application Specialist
*   **Task:** Build the `leash` command-line tool for managing the daemon.
*   **Outputs:**
    *   A binary crate `leash`.
    *   Subcommands for `start`, `stop`, `status`, `policy add`, `audit list`, etc.
    *   This CLI will use the `leash-ai-client` crate to communicate with the daemon.
*   **Dependencies:** `leash-ai-client`, `clap`.

---

## Phase 3: Integration & Hardening

This phase begins once the parallel workstreams from Phase 2 are functionally complete.

*   **Task:** Integration testing, end-to-end (E2E) test suite development, dependency injection, and configuration management.
*   **Agent Focus:** Integration & QA Specialist
*   **Outputs:**
    *   A stable, tested application.
    *   A comprehensive test suite that runs in CI.
    *   Finalized configuration files (`config.toml`).
    *   Documentation on how to build, run, and deploy the entire system.
